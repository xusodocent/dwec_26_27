    Setmana 8: sistema de rols en Vue Router, pas a pas

    Aquest contingut complementa els apunts de router. Un rol és una dada de l'aplicació; Vue Router no crea ni interpreta rols automàticament. Nosaltres decidim què significa lector o organitzador i escrivim un guard que compara la sessió amb les metadades de la ruta.

    Objectiu: restringir la navegació al panell i entendre què protegeix cada capa.

    Abans de començar: han de funcionar login, sessió i totes les vistes de les setmanes anteriors. Consulta Router, router avançat i les fonts oficials sobre meta i guards.

    1. D'on ix el rol?

    db.json conté comptes preparats amb una propietat rol. Un login correcte retorna, simplificant:

    JSON
    1
2
3
4
    {
  "accessToken": "TOKEN_JWT",
  "user": { "id": 1, "email": "organitza@vall.test", "rol": "organitzador" }
}

    El servei posa el token i la identitat en session. currentUser() demana /users/1 amb Bearer, comprova que el token permet llegir la fitxa pròpia i actualitza la identitat amb les dades del fake server. No existeix /auth/me en aquest projecte.

    No uses el valor d'un select de login per decidir el rol. El login no pregunta «vols ser organitzador?»: el rol ve del compte facilitat. La sessió en memòria és compartida perquè les importacions del mòdul retornen el mateix objecte reactive().

    JavaScript
    1
    export const session = reactive({ token: '', user: null });

    La propietat rol no és un claim firmat del JWT d'aquest complement: és una dada d'usuari que consulta el client. El servidor pot validar el token sense aplicar els nostres rols de navegació.

    2. Declarar què exigeix cada ruta

    Afig metadades a les rutes de gestió:

    JavaScript
    1
2
3
4
5
    {
  path: '/gestio',
  component: AdminView,
  meta: { requiresAuth: true, roles: ['organitzador'] }
}
    Element Significat
    meta Objecte amb informació addicional triada per nosaltres
    requiresAuth: true Aquesta ruta exigeix iniciar sessió
    roles: ['organitzador'] Aquesta ruta només admet aquest rol en el client
    roles: ['lector','organitzador'] Exemple de ruta que admet els dos rols
    Sense roles, amb requiresAuth Exemple de ruta per a qualsevol usuari autenticat
    Sense requiresAuth Ruta pública en la convenció d'aquesta guia

    Els noms requiresAuth i roles són convencions nostres, no paraules reservades. Posar-los en la ruta no té cap efecte fins que el guard els consulta.

    En aquesta guia totes les rutes amb roles tenen també requiresAuth. Catàleg, detall, login, Accés no permés i pàgina no trobada són públiques. No protegim /login amb el mateix guard per evitar redireccions circulars.

    3. Interceptar la navegació amb beforeEach

    Un guard global s'executa abans de confirmar una navegació. to és la ruta de destinació i to.fullPath inclou la ruta amb query i fragment. En Vue Router 4 podem retornar una destinació, false per cancel·lar o cap valor per continuar; no necessitem el patró next().

    Llig aquest recorregut amb el codi complet de més avall:

    1. Ruta pública: si no exigeix sessió, continua.
    2. Sense token: retorna /login i guarda to.fullPath en query.redirect.
    3. Amb token: espera currentUser(). Aquesta lectura protegida comprova el token al servidor abans d'entrar a la pantalla.
    4. 401 o 403 en la fitxa pròpia: neteja sessió i torna al login. Un 403 ací pot indicar una identitat local incoherent amb el token.
    5. Fallada de xarxa: informa i retorna false. No esborra una sessió només perquè el servidor estiga aturat.
    6. Rol no admés: retorna /sense-permis.
    7. Sessió i rol admesos: no retorna cap destinació; Vue Router confirma la navegació.

    import { createRouter, createWebHistory } from 'vue-router';
import { session, logout } from '../services/session.js';
import { currentUser } from '../services/api.js';
import CatalogView from '../views/CatalogView.vue';
import DetailView from '../views/DetailView.vue';
import EditorView from '../views/EditorView.vue';
import LoginView from '../views/LoginView.vue';
import AdminView from '../views/AdminView.vue';
import NotFoundView from '../views/NotFoundView.vue';
import ForbiddenView from '../views/ForbiddenView.vue';
const router = createRouter({ history: createWebHistory(import.meta.env.BASE_URL), routes: [
  { path: '/', redirect: '/reptes' },
  { path: '/reptes', component: CatalogView },
  { path: '/reptes/nou', component: EditorView, meta: { requiresAuth: true, roles: ['organitzador'] } },
  { path: '/reptes/:id', component: DetailView, props: true },
  { path: '/reptes/:id/editar', component: EditorView, props: true, meta: { requiresAuth: true, roles: ['organitzador'] } },
  { path: '/gestio', component: AdminView, meta: { requiresAuth: true, roles: ['organitzador'] } },
  { path: '/login', component: LoginView },
  { path: '/sense-permis', component: ForbiddenView },
  { path: '/:pathMatch(.*)*', component: NotFoundView },
] });
router.beforeEach(async to => {
  if (!to.meta.requiresAuth) return;
  if (!session.token) return { path: '/login', query: { redirect: to.fullPath } };
  try { await currentUser(); }
  catch (error) {
    if (error.status === 401 || error.status === 403) { logout(); return { path: '/login', query: { redirect: to.fullPath } }; }
    // Una fallada de xarxa cancel·la la navegació i mostra el problema.
    window.alert(error.message); return false;
  }
  if (to.meta.roles && !to.meta.roles.includes(session.user.rol)) return '/sense-permis';
});
export default router;

    4. Tornar a la destinació pendent després del login

    Un visitant que escriu /gestio acaba en /login?redirect=/gestio. Després d'entrar, LoginView llig la destinació i només accepta rutes internes conegudes:

    JavaScript
    1
2
3
    const dest = this.$route.query.redirect;
const safe = typeof dest === 'string' && /^\/(gestio|reptes)(\/|$)/.test(dest);
await this.$router.replace(safe ? dest : '/reptes');

    Aquesta comprovació evita usar la query com una destinació externa lliure. La ruta pendent encara passa pel guard: si ha entrat un lector, /gestio acaba en Accés no permés. replace() evita deixar el login com a pas immediat de tornada en l'historial.

    5. Amagar els controls segons rol

    En App.vue:

    Vue
    1
2
3
    <RouterLink v-if="session.user?.rol === 'organitzador'" to="/gestio">
  Gestió
</RouterLink>

    Aquesta expressió només mostra l'enllaç al rol adequat. Amagar un botó no impedeix escriure la URL: el guard és el que controla la navegació. El detall també condiciona l'enllaç Edita. No repetim tota la comprovació d'autenticació en cada botó; centralitzem-la en el router i el servei.

    6. Matriu de navegació

    Ruta Visitant Lector Organitzador
    /reptes i /reptes/:id Continua Continua Continua
    /gestio Login Accés no permés Continua
    /reptes/nou Login Accés no permés Continua
    /reptes/:id/editar Login Accés no permés Continua

    Prova cada combinació entrant la URL directament, no només amb els enllaços. En la demo les mateixes rutes van després de #, per exemple #/gestio.

    7. La prova clau: router i servidor tenen responsabilitats diferents

    1. Entra com a lector i intenta visitar /gestio: el guard ho denega.
    2. Fes login com a lector en Postman i copia el JWT.
    3. Envia POST /reptes amb aquell Bearer i un repte complet de prova: l'API respon 201.
    4. Elimina el repte amb DELETE perquè la prova no deixe dades sobrants.
    5. Repeteix POST sense token: 401.

    La regla reptes: 664 comprova autenticació, però no la propietat rol. Per això un lector autenticat pot fer l'escriptura manual. Aquesta és la resposta esperada, no un error que hages de corregir amb middleware.

    Capa Què comprova en el projecte
    Menú amb v-if Quins controls es mostren
    Guard amb meta.roles A quines pantalles permet navegar el client
    json-server-auth amb 664 Si l'escriptura porta un token vàlid
    Backend de producció, fora d'abast També hauria de comprovar el permís o rol per a cada operació

    Els rols del client i les regles numèriques del complement no són equivalents. El registre del complement admet propietats addicionals d'usuari; no es pot usar per construir un sistema segur d'alta d'administradors sense validació al servidor. En aquesta pràctica usem els comptes preparats i no programem registre ni gestió de rols.

    8. Activitat d'autoaprenentatge

    1. Explica què passaria si eliminares beforeEach però mantingueres meta.roles.
    2. Canvia temporalment els rols de /gestio a ['lector','organitzador']: comprova que el lector hi entra escrivint la URL. Restaura després la versió original. El menú continua ocult perquè encara té el seu propi v-if.
    3. Lleva temporalment la comprovació del menú i mantín el guard: el lector veu l'enllaç però no entra. Restaura'l.
    4. Documenta la prova manual POST amb el lector i explica per què un rol del router no protegeix una API.
    5. Prova el token caducat segons Setmana 9: la lectura protegida neteja la sessió i redirigeix al login.
